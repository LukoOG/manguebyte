# Test files

`stereo16.wav` and `mono24.wav` are the sources. They were generated by a
script: sines, silence, identical channels, noise and a decaying tone, chosen
to make an encoder use every kind of frame it has.

The other files were encoded from them with FFmpeg 7.1:

```bash
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a flac -compression_level 0 stereo16-level0.flac
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a flac -compression_level 5 stereo16-level5.flac
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a flac -compression_level 12 -frame_size 1152 stereo16-level12.flac
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a flac -compression_level 5 -frame_size 128 stereo16-blocks128.flac
ffmpeg -i mono24.wav   -map_metadata -1 -bitexact -c:a flac -sample_fmt s32 -bits_per_raw_sample 24 mono24.flac
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a pcm_s16be -f aiff stereo16.aiff
ffmpeg -i mono24.wav   -map_metadata -1 -bitexact -c:a pcm_s24be -f aiff mono24.aiff
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a pcm_s16le -f aiff stereo16-sowt.aifc
ffmpeg -i stereo16.wav -map_metadata -1 -bitexact -c:a pcm_s16le -rf64 always stereo16-rf64.wav
```

They exist so that the decoders are checked against an encoder written by
someone else. Do not regenerate them with this crate's own writers.

`stereo16-blocks128.flac` has 69 short frames where the others have 1 to 8,
which is what seeking needs to be tested on. `stereo16-rf64.wav` has the
64-bit header that WAV files past 4 GiB use, on a file of ordinary size.

## What the tests make for themselves

FFmpeg writes neither seek tables nor blocks of varying size, and a file long
enough to test seeking by bisection would be too large to keep here. So
`tests/common/mod.rs` builds such streams when the tests run:

- `write_flac` writes FLAC with the two simplest kinds of subframe, with any
  block sizes, seek table and header fields a test asks for.
- `repeat_flac` copies the frames of `stereo16-blocks128.flac` many times
  over, renumbered and with their checksums worked out again, so that a long
  stream still consists of frames FFmpeg compressed.
- `with_seek_table` adds a seek table to one of FFmpeg's files.

Since these come from this repository, they were shown to another decoder
once, by hand. This writes them, together with the files `AudioWriter`
produces, to a directory:

```bash
MANGUEBYTE_DUMP_DIR=/some/dir cargo test -p manguebyte-formats --test streaming -- --ignored
```

With FFmpeg 7.1, run with `-xerror -err_detect +crccheck+explode` so that
any checksum or syntax error is fatal:

- every stream `write_flac` makes for the tests decodes without a warning to
  exactly the samples the tests expect, from the start and from a seek
  (`-ss`) a quarter of the way in: mono to eight channels, 8 to 32 bits,
  fixed and varying block sizes, with and without a seek table or a declared
  length, and one whose first frame is numbered 1000;
- the stream `repeat_flac` makes decodes to the source audio once per round,
  and `stereo16-level12.flac` with a seek table added decodes to the source,
  whole and from `-ss 0.1`;
- the WAV, RF64 and AIFF files `AudioWriter` writes in each of its sample
  formats are read as the right format, rate, channels and length, and the
  RF64 ones decode to the same samples as the plain ones;
- for the same audio, the RF64 header `AudioWriter` writes is byte for byte
  the 80 bytes at the start of `stereo16-rf64.wav`, and the 16-bit AIFF file
  it writes is byte for byte `stereo16.aiff`;
- the files `AudioWriter` leaves when `finish` is never called (the
  `unfinished-*` files) decode to the same samples as the finished ones in
  every sample format. The AIFF ones do so even with `-xerror`; FFmpeg gives
  their duration as 13:31:35, worked out from the stand-in frame count
  0x7FFFFFFF. The WAV ones need FFmpeg run without `-xerror`: it warns
  "Ignoring maximum wav data size" and marks the last packet, which comes up
  short of the size the header states, as corrupt. With the frame count of
  an unfinished AIFF set to all ones instead, FFmpeg refuses to open the
  file ("Operation not permitted"), which is why the writer does not use
  all ones there.

## What this crate's FLAC encoder wrote

The `encoder-*.flac` files go the other way: this crate wrote them, and
FFmpeg 7.1 decoded them to the same samples, so the tests can check that
the decoder still reads what the encoder made and FFmpeg accepted.

- `encoder-stereo16-level0.flac`: `stereo16.wav` at level 0, no padding,
  room for one seek point. Fixed predictors only, in blocks of 1152.
- `encoder-mono24-level8.flac`: `mono24.wav` at level 8, the same options.
  Linear prediction up to order 12.
- `encoder-6ch-20bit.flac`: six channels of 2345 samples at 20 bits and
  22.05 kHz, worked out by `six_channels` in `tests/flac_encoder.rs` (a
  tone, the tone later and quieter, silence, a square wave, a ramp, quiet
  noise), at level 2 in blocks of 1000 with a `TITLE` tag. Its last block
  is short and its block size has no code of its own.

All three are written by the ignored test that also makes the files below:

```bash
MANGUEBYTE_DUMP_DIR=/some/dir cargo test -p manguebyte-formats --test flac_encoder -- --ignored
```

A later version of the encoder may compress differently; these stay as they
were checked.

## What FFmpeg made of the encoder's output

That test writes 243 FLAC files, each with its samples as raw 32-bit
integers and a line in `manifest.txt`. They were checked by hand with
FFmpeg 7.1, by a script that for each file

- ran `ffmpeg -v error -i FILE.flac -f null -` and required it to print
  nothing;
- decoded it with `-v error -xerror -err_detect +crccheck+explode` to
  `s32le`, required that to print nothing as well, and compared the samples
  with the expected ones (FFmpeg left-aligns them: a sample of `b` bits comes
  back multiplied by `2^(32 - b)`, and the low bits were checked to be zero);
- computed the MD5 of the samples FFmpeg decoded, packed as RFC 9639 says
  (interleaved, little-endian, sign-extended to whole bytes), with Python's
  `hashlib`, and compared it with the digest in the stream information.
  FFmpeg does not check that digest itself: a file with its digest changed
  decodes without a word.

The files cover levels 0 to 8 at 8, 16, 24 and 32 bits with silence,
full-scale square waves, white noise and sine sweeps; every depth from 4 to
32 bits; one to eight channels; blocks of 16, 17, 192, 256, 1000, 4608,
16384 and 65535 samples; rates of 1, 7, 8000, 11000, 11025, 22050, 88200,
192000, 352800, 705600 and 1048575 Hz, which use every kind of rate code
and none; streams of 0, 1, 2, 15, 16 and 17 samples; 32-bit channels
pinned at opposite ends of the range, so that the side channel needs 33
bits; samples with three low bits always zero; a seek table that had to
thin itself out, with tags; the largest metadata blocks the format allows,
16,777,215 bytes of padding, and a seek table of 932,067 points of which
the 932,066 unused ones became padding; the output of `AudioWriter` written
in random pieces, and one never finished.

238 passed every check. Among them, the unfinished stream decodes to every
complete frame and states no checksum (all zeros, which means unknown), as
intended. The other five are the files whose frames are larger than
208,012 bytes: 16-bit stereo noise in blocks of 54000, 56000, 60000 and
65535 samples, and a sweep beside noise in blocks of 65535, with frames of
216,012 to 262,152 bytes. FFmpeg returns no samples from them and reports
no error; the same noise in blocks of 52000 samples, frames of 208,012
bytes, decodes correctly. These frames are valid and this crate reads them;
no level makes them, since they need blocks far beyond the streamable
subset.

### Size against FFmpeg's encoder

`music.raw`, written by the same test, is five seconds of the synthetic
music `music` makes in `tests/flac_encoder.rs`, as 16-bit stereo at
44.1 kHz. FFmpeg encoded it with

```bash
ffmpeg -f s16le -ar 44100 -ac 2 -i music.raw -map_metadata -1 -bitexact -c:a flac -compression_level N out.flac
```

Bytes of audio frames, metadata left out, out of 882,000 bytes of samples:

| Level | FFmpeg 7.1 | This crate | Ratio |
|---|---|---|---|
| 0 | 568,369 | 533,210 | 0.938 |
| 1 | 535,151 | 532,503 | 0.995 |
| 2 | 533,417 | 532,491 | 0.998 |
| 3 | 502,383 | 500,247 | 0.996 |
| 4 | 496,178 | 492,882 | 0.993 |
| 5 | 492,876 | 492,265 | 0.999 |
| 6 | 492,438 | 487,100 | 0.989 |
| 7 | 492,535 | 483,742 | 0.982 |
| 8 | 490,211 | 482,807 | 0.985 |

FFmpeg's levels 9 to 12 give 489,781, 489,756, 488,119 and 487,535.
`compression_is_within_a_few_percent_of_ffmpegs` keeps FFmpeg's figures for

This encoder's levels 1 and 2 differ only in how the stereo coding of each
block is chosen: level 2 codes all four and keeps the smallest, level 1
picks one from an estimate. The estimate costs level 1 the 12 bytes between
them here; the same test checks that level 2 is never the larger.

## Lossy files

The Ogg Vorbis and MP3 files were encoded from audio the tests make: the
functions of `tests/common/lossy.rs` (`lossy_signal`, `lossy_tones` and
`lossy_bursts`), at the lengths `source` there gives. The ignored test
`write_the_sources_of_the_lossy_files` writes them as 32-bit float WAV:

```bash
MANGUEBYTE_DUMP_DIR=/some/dir cargo test -p manguebyte-formats --test lossy -- --ignored
```

- `signal-*`: three partials of a tone, a sweep from 40 Hz to three tenths
  of the sample rate, silence, white noise, then clicks over a quiet tone;
  each channel at its own pitch with its own noise. The lengths are odd:
  110257 frames at 44.1 kHz, 44111 at 22.05 kHz, 57601 at 48 kHz, 12007 at
  8 kHz, 48013 at 96 kHz, 40003 at 32 kHz, 30011 at 24 kHz, 20021 at
  16 kHz, 16005 at 11.025 kHz and 15013 at 12 kHz.
- `tones-*`: a chord of three steady tones per channel, one second long, or
  100 frames for `tones-2ch-44100-short`.
- `bursts-1ch-8000`: 150 seconds of silence broken every quarter of a
  second by a burst of 40 ms whose pitch climbs, 1200005 frames.

### Ogg Vorbis

Each was encoded with FFmpeg 7.1 and its libvorbis:

```bash
ffmpeg -i signal-2ch-44100.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 3 -metadata TITLE="Test signal" -metadata ARTIST="Manguebyte" vorbis-2ch-44100-q3.ogg
ffmpeg -i signal-1ch-22050.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 0 vorbis-1ch-22050-q0.ogg
ffmpeg -i signal-6ch-48000.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 2 vorbis-6ch-48000-q2.ogg
ffmpeg -i signal-1ch-8000.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 5 vorbis-1ch-8000-q5.ogg
ffmpeg -i signal-2ch-96000.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 4 vorbis-2ch-96000-q4.ogg
ffmpeg -i tones-2ch-48000.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 10 vorbis-tones-2ch-48000-q10.ogg
ffmpeg -i tones-2ch-44100-short.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 4 vorbis-2ch-44100-100frames.ogg
ffmpeg -i bursts-1ch-8000.wav -map_metadata -1 -bitexact -c:a libvorbis -q:a 0 vorbis-1ch-8000-bursts.ogg
```

FFmpeg read the six-channel WAV, which has no channel mask, as 5.1, and
handed libvorbis its channels in the Vorbis order, so the file holds them
as Vorbis defines 5.1. With `-bitexact`, FFmpeg writes `ffmpeg` as the
vendor of the comment header and adds a comment `encoder=Lavc libvorbis`.

What the tests found, and hold the decoder to with a margin, is in
`tests/vorbis.rs`. Two things there are the encoder's and not the
decoder's: libvorbis gives steady tones back up to 1 % louder than it was
given them, and in 5.1 it codes the LFE channel only up to about 280 Hz.

The files here have residues of type 1 and 2 only, and codebooks whose
vectors come from a lattice. `tests/vorbis_streams.rs` writes streams of
its own for the rest (residues of type 0, codebooks that list their
vectors, floors of type 0, 255 channels), as `tests/common/vorbis.rs`
says.

```bash
ffmpeg -i signal-2ch-44100.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 128k mp3-2ch-44100-cbr128.mp3
ffmpeg -i signal-2ch-44100.wav -map_metadata -1 -bitexact -c:a libmp3lame -q:a 2 mp3-2ch-44100-vbr2.mp3
ffmpeg -i tones-2ch-48000.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 320k mp3-tones-2ch-48000-320.mp3
ffmpeg -i signal-1ch-22050.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 64k mp3-1ch-22050-64.mp3
ffmpeg -i signal-2ch-24000.wav -map_metadata -1 -bitexact -c:a libmp3lame -q:a 4 mp3-2ch-24000-vbr4.mp3
ffmpeg -i signal-1ch-16000.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 32k mp3-1ch-16000-32.mp3
ffmpeg -i signal-2ch-11025.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 32k mp3-2ch-11025-32.mp3
ffmpeg -i signal-1ch-12000.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 24k mp3-1ch-12000-24.mp3
ffmpeg -i signal-1ch-8000.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 16k mp3-1ch-8000-16.mp3
ffmpeg -i signal-2ch-32000.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 96k -joint_stereo 0 mp3-2ch-32000-stereo96.mp3
ffmpeg -i signal-2ch-44100.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 160k -reservoir 0 -write_xing 0 -write_id3v1 1 mp3-2ch-44100-plain160.mp3
ffmpeg -i tones-2ch-44100-short.wav -map_metadata -1 -bitexact -c:a libmp3lame -b:a 128k mp3-2ch-44100-100frames.mp3
ffmpeg -i tones-2ch-44100-short.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 128k -f mp2 mp2-2ch-44100.mp2
```

These cover MPEG-1 at 32, 44.1 and 48 kHz, MPEG-2 at 16, 22.05 and 24
kHz, and MPEG-2.5 at 8, 11.025 and 12 kHz; mono, joint stereo (LAME's
default, which codes bands as mid and side) and plain stereo; constant and
variable bitrates; short blocks, which LAME switches to at the clicks; and
the bit reservoir, turned off for `plain160`. Every file starts with the
ID3v2.4 tag FFmpeg writes, of ten bytes of padding, and all but `plain160`
with a frame of silence holding a Xing or Info header and a LAME tag that
says LAME added 576 samples before the audio. `plain160` has neither, and
no ID3v1 tag either: FFmpeg writes one only when there is something to put
in it. `mp2-2ch-44100.mp2` is layer II, by FFmpeg's own encoder, to check
that it is refused.

What the tests found is in `tests/mp3.rs`. Two things there are the
encoder's and not the decoder's: in constant bitrate up to 160 kbit/s, LAME
scales what it encodes by 0.95, which the level of the tones shows to four
places (at 320 kbit/s and in variable bitrate it does not); and the LAME tag
FFmpeg wrote into the 12 kHz file states 15023 samples, ten more than the
source has, while it states the length exactly in every other file.

LAME writes no intensity stereo, no mixed blocks and no CRC, and nothing
here writes a VBRI header. `tests/mp3.rs` makes what it needs of those from
these files: a CRC added to each frame of `plain160` that has two bytes to
spare, a VBRI header put in place of an Info frame, bytes that are not
frames between two frames. Intensity stereo and the reordering of short
blocks are checked by the unit tests of `src/mp3/layer3.rs`, against the
formulas of the standard.

### Layer II

FFmpeg's own encoder (`mp2`), from the same sources, one file for each
allocation table of ISO/IEC 11172-3 and the one of 13818-3:

```bash
ffmpeg -i signal-2ch-44100.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 192k -f mp2 mp2-2ch-44100-192.mp2
ffmpeg -i tones-2ch-48000.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 96k -f mp2 mp2-tones-2ch-48000-96.mp2
ffmpeg -i signal-2ch-32000.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 64k -f mp2 mp2-2ch-32000-64.mp2
ffmpeg -i signal-2ch-32000.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 160k -f mp2 mp2-2ch-32000-160.mp2
ffmpeg -i signal-1ch-22050.wav -map_metadata -1 -bitexact -c:a mp2 -b:a 64k -f mp2 mp2-1ch-22050-64.mp2
```

They take tables B (96 kbit/s a channel at 44.1 kHz), C (48 at 48 kHz),
D (32 at 32 kHz), A (80 at 32 kHz) and the table of the lower sample
frequencies; `mp2-2ch-44100.mp2`, above, takes table A at 44.1 kHz.
FFmpeg writes stereo, not joint stereo, and no CRC; FFmpeg has no layer I
encoder. `tests/common/mpeg12.rs` writes what is missing.

Their decodes were compared once, by hand, with FFmpeg 7.1's decoder
(`ffmpeg -i FILE.mp2 -c:a pcm_f32le FILE.wav`), and with two more files
made the same way (`signal-1ch-22050.wav` resampled to 44.1 kHz at
64 kbit/s, table A in mono, and `signal-2ch-24000.wav` at 96 kbit/s):
every file decodes to the same number of samples, from the same first
sample, within 84 to 86 dB of FFmpeg's decode and never further from it
than 3.2e-5, which is FFmpeg's own rounding to 16 bits.

### Formats the system decodes

For `tests/platform.rs`, from the same sources, with FFmpeg 7.1's own
encoders:

```bash
ffmpeg -i tones-2ch-44100.wav -map_metadata -1 -bitexact -c:a aac -b:a 128k aac-tones-2ch-44100.m4a
ffmpeg -i tones-2ch-44100.wav -t 0.25 -map_metadata -1 -bitexact -c:a alac -sample_fmt s16p alac-tones-2ch-44100.m4a
ffmpeg -i signal-1ch-22050.wav -map_metadata -1 -bitexact -c:a aac -b:a 64k -f adts aac-1ch-22050.aac
ffmpeg -i tones-2ch-44100.wav -map_metadata -1 -bitexact -c:a wmav2 -b:a 128k wma-tones-2ch-44100.wma
```

FFmpeg rounds the float samples to 16 bits for ALAC, half to even, which
is how the test works out the samples the ALAC file must give back. Its
AAC encoder puts 1024 frames of priming first, which the MPEG-4 file's
edit list states and the ADTS file cannot, and uses noise substitution
(PNS), which Media Foundation decodes with noise of its own after every
seek: the same file encoded with `-aac_pns 0` seeks to within 1e-4 of a
decode from the start everywhere (checked by hand), where this one comes
within 4.2e-2 in its last few hundred frames. The WMA decoder gives 43008
frames of the 44100 the file states.

## Metadata

The `meta-*` files hold tags that another program wrote, for
`tests/metadata.rs` to read. Their audio is a tone FFmpeg 7.1 generated
(`lavfi`), and the picture a PNG of 4 by 2 red pixels it generated too:

```bash
ffmpeg -f lavfi -i "color=c=red:s=4x2" -frames:v 1 -bitexact cover.png
ffmpeg -f lavfi -i "sine=frequency=440:sample_rate=8000:duration=0.05" -c:a pcm_s16le -write_bext 1 \
  -metadata title="Frevo" -metadata artist="Manguebyte" -metadata album="Tests" -metadata date="2026" \
  -metadata comment="A comment" -metadata copyright="(C) 2026" -metadata genre="Frevo" -metadata track="4" \
  -metadata description="A test tone" -metadata originator="FFmpeg" -metadata originator_reference="MB-1" \
  -metadata origination_date="2026-10-17" -metadata origination_time="12:34:56" \
  -metadata time_reference="480000" -metadata coding_history="A=PCM,F=8000,W=16,M=mono" \
  -bitexact meta-info-bext.wav
ffmpeg -f lavfi -i "sine=frequency=440:sample_rate=8000:duration=0.05" -i cover.png -map 0 -map 1 \
  -c:a flac -c:v copy -disposition:v attached_pic -metadata title="Maracatu" -metadata artist="Nação Zumbi" \
  -metadata album="Da Lama ao Caos" -metadata date="1994" -metadata track="3/12" -metadata genre="Manguebeat" \
  -metadata BPM="96" -metadata:s:v comment="Cover (front)" -metadata:s:v title="Capa" -bitexact meta-tags-picture.flac
ffmpeg -f lavfi -i "sine=frequency=440:sample_rate=8000:duration=0.2" -i cover.png -map 0 -map 1 \
  -c:a libmp3lame -b:a 16k -c:v copy -disposition:v attached_pic -metadata title="Ciranda" \
  -metadata artist="Lia de Itamaracá" -metadata album="Eu Sou Lia" -metadata date="2000" -metadata track="1/10" \
  -metadata genre="Ciranda" -metadata TBPM="104" -metadata TKEY="Am" -metadata comment="Ciranda de praia" \
  -metadata:s:v title="Capa" -metadata:s:v comment="Cover (front)" -bitexact meta-id3v24.mp3
ffmpeg -f lavfi -i "sine=frequency=440:sample_rate=8000:duration=0.2" -c:a libmp3lame -b:a 16k \
  -id3v2_version 3 -write_id3v1 1 -metadata title="Coco" -metadata artist="Selma do Coco" \
  -metadata album="Minha Ciranda" -metadata date="1998" -metadata track="7" -metadata genre="Folk" \
  -metadata comment="Old tags" -bitexact meta-id3v23-v1.mp3
```

What FFmpeg made of them, which the tests hold the reader to: the WAV
file has a `bext` chunk of version 1 before its samples and a `LIST/INFO`
after the `bext`, with the track number as `IPRT`; the FLAC file has its
picture block before its Vorbis comment and 8192 bytes of padding; the
MP3 files carry the comment as a `TXXX` frame described `comment`, not as
`COMM`, and the ID3v1 tag numbers the genre 80, one of Winamp's additions
to the 80 genres of ID3v1, which the reader does not name. FFmpeg writes
no AIFF text chunks, cue points, `smpl` or `iXML`; those are checked by
writing them and reading them back.
